### Overview

**Hub detection** is the sub-step of Pass 4 that identifies the small set of L3 pages whose structural role in the cross-link graph qualifies them as canonical entry points. Hubs receive elevated retrieval weight, Opus-tier review during Pass 4, and L1 routing manifest promotion. Most pages are not hubs — hub set sizing should stay under ~10% of pages.

A hub answers one of three structural questions:

- **"Which page do many other pages cite?"** (inbound-degree hub — a single feature/decision that downstream pages reference)
- **"Which page bridges across multiple clusters?"** (bridge hub — a cross-domain concept like `auth-token-rotation` that pulls together auth + crypto + ops)
- **"Which page should exist but is targeted as a dangling wikilink?"** (convergent-dangling hub-candidate — a missing concept that multiple pages assume exists)

The third category is what drives create-page candidate generation; see [[4 - Graph Linking Materialisation]] Step 4.

##### Interaction with Provenance Graph

Hub detection runs over the **union of the L0 provenance graph and the L4 wikilink graph**. Pure-provenance hubs (a heavily-imported code file) and pure-wikilink hubs (a feature page cited by many synthesized pages) both qualify. The union lets Pass 4 catch hubs that neither graph alone would surface — e.g. a feature page wikilinked by 8 other pages whose underlying code modules also have high PageRank.

### Promotion Criteria

A page is promoted to hub when **any** of the following thresholds are met. All are tunable per workspace.

| Criterion | Default threshold | Rationale |
|---|---|---|
| **Inbound-edge count** | ≥ 10 typed L4 inbound edges | Many pages reference it; canonical entry point candidate |
| **Cluster-link count** | links to ≥ 2 distinct clusters | Bridges domains; cross-domain knowledge hub |
| **Convergent-dangling count** | ≥ 5 pages dangle on its slug before resolution | Pages assume the concept exists; even if no page exists yet, the slug is a hub-in-waiting |
| **Inbound PageRank** | top 5% of pages by L4 PageRank | Catches structural prominence missed by raw degree count |
| **Bridge score** | top 10% per cluster (see Pass 4 Step 5) | Cross-cluster importance |
| **Source-class diversity** | inbound edges originate from ≥ 3 distinct source classes (code + Slack + Notion + ADR, etc.) | Strong cross-domain signal |

Promotion is **not additive** — a page meeting any single criterion is a hub. The criteria overlap heavily for true hubs; meeting one usually means meeting several.

---

### Scoring

Each hub gets a numeric `hub_score` for ranking within the hub set (used by retrieval and L1 manifest priority):

```
hub_score =
    (inbound_edge_count_normalized × 0.35) +
    (cluster_link_count × 0.20) +
    (bridge_score_normalized × 0.20) +
    (inbound_pagerank_normalized × 0.15) +
    (source_class_diversity × 0.10)
```

All inputs normalized to `[0, 1]` against the workspace's hub-set distribution. Weights tunable; the defaults reflect that raw inbound-edge count is the strongest signal but cross-domain bridging and PageRank add useful precision.

---

### Hub Designation in the Cluster Manifest

Each cluster has at most one **primary hub** and a small set of **satellites**. The primary hub is the highest-`hub_score` page in the cluster; satellites are the next 2–4 ranked hubs.

```yaml
HubDesignation:
  cluster_id: <ref>
  primary_hub: <page_id>
  satellites: [<page_id>, ...]      # 0–4 secondary hubs
  hub_score: <float>                # primary hub's score
  designation_method: degree | bridge | dangling | pagerank | composite
  promoted_at: <iso8601>
```

`designation_method` records which criterion triggered promotion (useful for debugging and for SME communication: "this hub was selected because it bridges 4 clusters" reads better than "it's a hub").

---

### Edge Cases

| Case | Treatment |
|---|---|
| Cluster has no page meeting any criterion | `primary_hub = highest-importance_score page in cluster`; flagged `designation_method: fallback`. Pass 5 still renders the cluster summary. |
| Cluster has > 5 pages meeting hub criteria | Keep `primary_hub` + top 4 satellites; remaining hub-eligible pages get hub-bonus retrieval weight but aren't designated. Suggests cluster is too broad — re-cluster trigger fires. |
| Hub is itself a create-page candidate (dangling target) | Hub designation deferred until the page exists; create-page candidate is flagged "blocks hub designation" for prioritisation in the Pass-3-backfill queue. |
| Hub spans cluster boundary (cluster-link count ≥ 2) | Hub is "owned" by its primary cluster but listed as a `bridge` in the manifests of every cluster it links to. Pass 5 summaries on either side describe it. |
| Page meets hub criteria but is marked `skip_synthesis` | Cannot be a hub (no L3 page exists). The source's `importance_score` is logged but no hub designation. |
| Hub changes between Pass 4 runs (different page wins primary) | Old hub demoted to satellite (or dropped if it no longer meets any criterion). Demotion is logged for SME visibility — hubs flipping frequently is a workspace-health red flag. |

### Opus Allocation

Hubs are the **only** Pass 4 sub-step where Opus is the default tier (not just degraded-Haiku-on-budget-exhaustion). Specifically:

- **Typed edge classification** for edges where either endpoint is a hub uses Opus.
- **Contradiction detection** between a hub and any other page uses Opus.
- **Cross-cluster bridge classification** for hub-bridges uses Opus.

Rationale: hubs are read disproportionately at retrieval time. A miscategorised edge to a hub propagates wrong context to many downstream queries. The cost ratio justifies the model upgrade.

When Opus budget is exhausted:
1. Routine hub-edge classification falls back to Haiku.
2. Contradiction detection involving hubs falls back to Haiku **but** the contradiction is also queued for Opus re-verification once budget refreshes — never silently accepted.
3. Mechanical hub criteria (degree, dangling count) continue to run regardless of LLM budget — those are arithmetic.

---

### Quality Invariants

1. **Hub set < 10% of total pages.** If higher, criteria thresholds are too permissive.
2. **At least 60% of clusters have a designated primary hub** (not `fallback`). Below this, boundary detection in Pass 1 is over-fragmenting.
3. **Hubs span source classes.** A workspace where all hubs are code pages indicates a connector imbalance — Slack/Notion/ADR sources aren't getting wikilinks or aren't being classified as boundaries.
4. **Hub designations stable across consecutive Pass 4 runs on unchanged inputs.** Re-running Pass 4 on the same graph should pick the same primary hub. Flapping = non-determinism = bug.
5. **Hub promotion is logged and reversible.** Every promotion writes an event; every demotion writes an event. SMEs can audit the hub history.

---

### Downstream consumers

- **Pass 5** uses `primary_hub` + `satellites` to populate `hub_designation` in the community summary.
- **L1 routing manifest** promotes hubs to canonical route targets (`load: <hub_page_id>` becomes the first entry for any matching route).
- **Retrieval ranker** applies a hub-bonus weight (typically +20% on relevance score for hub pages).
- **Onboarding surfaces** treat `primary_hub` of each cluster as the "start here" entry.
- **L5 drift loop** prioritises hub-page resynthesis ahead of satellite pages.
