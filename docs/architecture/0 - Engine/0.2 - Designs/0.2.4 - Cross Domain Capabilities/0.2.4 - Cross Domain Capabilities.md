#### Overview

Represented Visually In [[0 - Wiki Diagram]]

Every single workspace (grouped by `workspace_id`) will be treated as its own Wiki. 
- Enforces a natural separation boundary
- Allows for easier cross-domain linkage, as there is a centralised source of truth compiled of all source pages
- The wiki itself represents the engineering team as the abstract overarching concepts
	- Many multi-directory wikis are used to represent different abstraction domains (ie. Personal v Business v Hobby) 

This therefore means
- One singular repository of [[0.0.0 - Source File]]
- One singular repository of [[0.0.4 - Graph Link Index]]
- One singular [[0.0.1 - Routing Manifests]] 
	- Centralised router to route to the associated domain
- Every single `Domain` is a computed hub instead of a narrowly declared subset
	- Every `Domain` will generate its own [[0.0.2 - Community Summaries]] 
	- The domain will act as a natural boundary within the workspace and will generate a `domain_id` within the workspace
- Every page is bounded by `workspace_id` and `domain_id` 
	- Domain ID reflects the natural boundary that each individual community summary aggregates
	- This allows for greater cross-referencing, as all domains have access to a central repository of source pages, but can also link to other pages as per [[Canonical Promotion Gates]] or if the page instead references the intended source page and covers the same domain as this source page

#### Worst Case & Trade-offs
- **Enterprise Level Scaling**
	- At larger level companies (~100k pages >)
- **Massive Recompute Churn**
- **Per Product Separation**
	- This implementation is leaning towards a product being associated with the `workspace_id`
	- this is not appropriate for multi-product or multiple engineering team orgs
		- each product would need to represent its own workspace => one org now controls many workspaces (*enterprise edition*)
